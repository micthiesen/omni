# Fond: request webhook connected to Kitchen

Session of 2026-11-19. Brief: connect Fond's `recipe.request` webhook to the Kitchen bot in
the self-hosted Rakazo on boris (`~/compose/rakazo`), with a daily sweep, end to end. Earlier
history: `PROGRESS-requests.md` (the feature and the webhook's contract).

No key, token or webhook address is in this file, in git, or was printed at any point.

## What was created

In Rakazo, on the Kitchen bot (`cmwn8imvu62yk2y9emn78yhu4`), which had no routines and no
webhook key before:

| Routine | Id | Trigger |
| --- | --- | --- |
| Fond requests | `cmwnicrpk000u07l7okbqmczk` | webhook, active, no schedule |
| Fond requests daily sweep | `cmwnicrw4000v07l7ou92rt7s` | cron `0 8 * * *`, America/Vancouver, active |

- Both run alongside Kitchen's chat with notifications on and no model override, like the
  other webhook routines on this server (Inbox, Health, Business, Systems, Chief).
- "Fond requests" has the prompt from the brief, word for word. The sweep has the same prompt
  with this in front: "Daily sweep of Ask Kitchen requests in Fond. Handle only requests that
  have been queued for more than 15 minutes (createdAt more than 15 minutes ago); leave newer
  ones to the webhook routine."
- Kitchen's webhook key was generated by Rakazo (`bots.rotateWebhookSecret`) on boris and
  written straight into the env file below. A Rakazo bot has one webhook address and one key;
  every active webhook routine of the bot (here, one) runs on a delivery.

**How.** Rakazo has no CLI or admin token for this. Its supported path is the RPC API its own
app uses (`routines.create`, `bots.rotateWebhookSecret`), which needs a signed-in user. As in
the bot reorganization of 2026-11-13, the calls were made from inside the `api` container as
Michael through one temporary login session added to Rakazo's `session` table (three-hour
expiry, labelled `boris-agent-maintenance (fond webhook 2026-11-19)`), deleted when the work
was done. Nothing else in Rakazo's database was written by hand: the routines and the key
were created by the API, so the sweep's next run was computed and queued by Rakazo itself. No
Rakazo service needed a restart.

## Restart

`docker compose up -d omni` on boris, under the maintenance lock, no prune.

**It also recreated `plex`, which was not intended.** Compose brings a service's dependencies
up to date before the service, `omni` depends on `plex`, and Compose judged the running plex
container out of date, so it recreated it (05:10 MST). Plex took longer than Compose's wait to
report healthy, so that first command failed and left `omni` created but stopped for about
five minutes. `docker compose up -d --no-deps omni` then started it. Plex has been healthy
since; radarr, sonarr and every Rakazo service were not touched. Anything playing on Plex at
05:10 was interrupted. For an env-only change to Omni, use `--no-deps`.

Boot log after the restart: "Recipe requests are announced to the configured webhook", with
the host only. Build `faa7128`.
