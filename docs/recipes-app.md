# Fond PWA

Fond's phone app is `crates/omni-recipes-web`: a Leptos 0.8 client-side app
built by trunk into its own bundle and served by Omni only on
`https://recipes.syas.ca`. It is installed from Safari with Share, Add to Home
Screen. It shares no code or styles with the Omni UI (`omni-web`,
`omni-web-kit`); its look is described in `docs/design-system.md`, "Fond".

The server side (`omni-recipes`) and the wire contract
(`crates/omni-api/src/fond.rs`) are described in `docs/recipes.md`.

## Structure

```
crates/omni-recipes-web/
  index.html, Trunk.toml       trunk entry; the post-build hook writes dist/sw.js
  manifest.webmanifest         id, scope and start_url "/", display standalone
  icons/                       generated by brand/icons.py (versioned file names)
  style/app.css                the whole stylesheet: tokens, light and dark
  js/boot.js                   loads the wasm bundle (no inline script)
  js/sw.js                     the service worker (constants prepended at build)
  js/idb.js                    IndexedDB wrapper, called through wasm-bindgen
  build/precache.sh            the trunk hook: precache list and build digest
  src/logic/                   pure decisions, unit-tested natively
    session.rs                 a cook session's state as a projection of its events
    outbox.rs                  queue order, batching, retry, unsent-edit overlay
    library.rs                 search words, tag filter, sorts, filter-sheet counts
    mod.rs                     routes, scale parsing and stepping, tile colours
  src/platform/                the browser: fetch, IndexedDB, service worker,
                               wake lock, timer sound, photo downscaling
  src/store.rs                 app state, sync, the outbox pump, the event stream
  src/ui/                      Library, Recipe, Cook, Inbox, Requests, the chart table
  dev/mock-server.py           the contract in memory, for development and tests
  e2e/                         Playwright tests (WebKit, iPhone size)
```

Everything derived from a recipe comes from `omni-recipe-format`, the crate
the server validates and renders with: `list_view` for the Steps view,
`chart_blocks` for the chart (the app only turns cell rectangles into
`rowspan`/`colspan`), `cook_marks`, `ready_steps`, `meanwhile`, `step_inputs`,
`gather_list`, `equipment` and the search tokeniser. Never reimplement layout,
scaling or rendering in the app.

JavaScript is three hand-written files with no dependencies and no CDN. Wake
lock, sound, canvas and service worker calls are made from Rust through
`web-sys`.

## Offline model

The phone holds the whole library in IndexedDB (database `fond`): `recipes`
(one `RecipeRecord` per id), `sessions` (open cook sessions with their
events), `outbox`, `blobs` (photo bytes waiting to upload) and `kv` (sync
sequence and server build, tag registry, last scale per recipe, the inbox
list, the document each session was started on, and stored originals once
viewed). All screens read from memory, loaded from IndexedDB at launch, so
the app renders without the network.

**Sync.** `GET /api/sync?since=<seq>` runs at launch, when the phone comes
back online or the app returns to the front, and whenever `/api/events` sends
`library` (or a `hello` whose `seq` differs). A `full` answer replaces the
library; otherwise changed recipes are stored and `removed` ids dropped. If
the recipe count then differs from `liveCount`, one full sync follows. A
`session` frame refetches that session.

**Writes.** Notes, archive and delete, session starts, session events and
photo uploads are applied to local state at once and appended to the outbox
with a client-generated id (`op_…`, `cook_…`, `ev_…`, `inb_…`). The outbox is
sent strictly in order: neighbouring record ops travel in one `POST /api/ops`,
neighbouring events of one session in one `POST /api/cook/:id/events`, photos
one at a time. No answer, 5xx, 408, 425 and 429 retry with backoff (1 s
doubling to 60 s); any other 4xx drops the entry, since the server will never
accept it and it would block everything behind it. The server applies each id
once, so a resend after a lost answer is safe. A sync always drains the
outbox first, and unsent edits are laid over synced records, so a sync never
undoes what is on screen.

A local change and the outbox entry that sends it are stored in one
IndexedDB transaction (`idb::atomic`, `idbTx` in `js/idb.js`), committed as
soon as the writes are issued: a note, an archive or delete, a session start
or a session event is on the phone with its entry or not at all, so a sync
never undoes a change that was not queued. As a second line, at launch any
session event found without an outbox entry is queued again.
Events for a session the server has not seen are answered 425 and stay
queued behind their start; when a start is refused for good, everything
queued for that session is dropped with it.

**Notes** are in the outbox on every keystroke (the unsent edit is replaced
in place) and sent after 800 ms without typing or when the field loses focus,
with the `baseRev` of the first unsent edit. When the server answers with the
text unchanged, later edits build on the new revision; when it kept both
texts, the field shows the merged text.

**Cook sessions** start on the phone, so cooking can begin offline. Every
view of a session is `logic::session::project` over its events; local events
not yet sent are appended after the server's. A session carries the document
of its pinned revision (`CookSession.doc`, set on the phone for a session
started there and sent by the server otherwise); it is stored with the
session and the cook stays on it until they switch to a newer revision
(`rebase`). Without one the app falls back to the recipe's head. A result
photo is uploaded under its stored blob name as the upload id, so a retry
stores it once.
Timers are end times in the log; the app rings (Web Audio and vibration)
while it is in front, and Omni's own alert covers the rest.
Running timers are docked under the cook screen and count up once they run
out; marking a step done stops its timer (`docs/fond/cook-chart-steps.md`).
A recipe with variants shows a picker under the scale ("As written" and each
variant's name); the page renders `variant_doc` of the chosen one, and Cook
starts the session with a `variant` event after `startCook`, so the session
cooks it on every device. Cook mode titles the screen "Title · Variant name"
and `Store::session_doc` applies the session's variant (the last `variant`
event) to its pinned document. While a variant is shown, on the recipe page
or in its cook, the amount sheet does not open: a toast says amounts change
the recipe as written.
A step's timer is one batch: a step with `repeat` labels its button "Start 9
min timer (one of 3 batches)" at the session's scale, and the cook starts it
once per batch. Step text, sizes, heat stages and counts (`{yield}`,
`{portions}`, `{batches}`) come from `omni-recipe-format`'s segments; the app
sets counts and settings in bold like amounts.
The Finish sheet also offers "Discard this cook", which asks once more and
then appends an `abandon` event: the session leaves "Cooking now", nothing is
logged and the recipe's cook count is unchanged.

Leaving cook mode with the close button asks what to do with the cook:
"Keep for later" (the session stays under "Cooking now"), "Discard this cook"
(one more confirmation, then `abandon`) or Cancel.

**Amounts.** The one edit of a recipe the app makes is the amount of an
ingredient (`ui/amount.rs`). Each ingredient line with an amount has a pencil;
in cook mode the pencil is on each Gather line with an amount, and a step
offers "Amounts" for the ingredients it uses. Cook mode has nothing
that changes a recipe for one cook only: the same sheet saves the same
revision, and the open session moves to it at once (a `rebase` event queued
behind the amount, `Store::change_amount`), so the new amount shows at the
session's scale without the "updated since you started" notice. Undo sends
the old amount back and the session follows again. A step also has "Recipe
notes", the recipe's notes field in a sheet, for anything that is not an
amount. The sheet takes a quantity ("2", "1.5", "1 1/2", "1½";
`omni_recipe_format::parse_qty`), a unit from the known units, "(count)" or
the ingredient's own, and the quick buttons ½×, ¾×, 1¼× and 2×; it previews
the ingredient line and saves only what the format's validator accepts. The
amount is always the recipe's as written: on a scaled page the sheet says so.
Saving puts the new revision on screen at once (`outbox::with_amount`, the
same `amount_ops` the server runs) and queues a `ClientOpKind::Amount`; a
sync that lands first has the queued change laid over it. A ten-second Undo
toast sends the old amount back as another op. A refusal from the server
restores the recipe it sends and shows its reason.

**The grid.** The library's cards are a masonry (`Masonry` in `ui/library.rs`): two columns
below 620px and three above, each a stack of cards at their own heights 22px apart, so the
columns end ragged and no row pads a short card up to a tall neighbour. The cards are dealt
across the columns in order (`logic::library::column`): card 1 left, card 2 right, card 3 left,
which keeps reading row by row in the sort order and needs no measuring, so the layout is
there on the first frame and the scroll position can be restored at once. In the DOM the
columns come one after the other. Covers keep their 4:3 shape and still load lazily a few at a
time. The width comes from `store.width`, kept by one `resize` listener.

**Pinned recipes.** "Pin" and "Unpin" are in the recipe's menu and in each card's menu (the
three dots on the card's cover, which also names the card for assistive tech: "More for
…"). Pinned recipes form a "Pinned" section above the grid, in their own order, and are left
out of the grid below; a search or a filter lists every match in one grid instead. The order is
changed by pressing and holding a pinned card (400 ms; a finger that moves 10px before then is
scrolling) and dragging it onto another's place: the card follows the finger as a copy, its
own place is dimmed, and the card under the finger is outlined as the place it will take.
Lifting the finger there stores the list; lifting anywhere else changes nothing. The cards do
not shuffle while one is held: moving the pressed element to another column would take it out
of the page, and with it the touch that is doing the dragging. A `touchmove` listener that is not passive keeps the page from scrolling
during the drag, the system's own link drag and long-press preview are switched off on cards,
the pointer is captured so a mouse let go outside the section still ends the drag, and the
click that follows the lift is swallowed so it does not open the recipe. Without a
drag, the card menu of a pinned card has "Move up" and "Move down", which stay open for
several moves. The list is the server's (`ClientOpKind::Pins`, the whole list each time, laid
over a sync until it is sent), so it is the same on every device and follows a change made
elsewhere like the rest of the library. Not built: scrolling the screen while dragging near
its edge (the section is at the top).

**Steppers.** A plus or minus button moves to the next amount its unit is measured in
(`omni_recipe_format::measure::step`): grams by 1 below 20, then 5, 10 from 100, 25 from 250
and 50 from 1 kg; millilitres by 5 up to 60, then 25, and 50 from 500 (there is no step of ten,
which the measuring rule flags); kilograms and litres by 0.05, 0.1 and 0.25; teaspoons and cups
by quarters and by halves from 2; tablespoons by halves and by one from 4; ounces by a half,
pounds by a quarter; anything counted by one (and to a half below one). An amount off the grid
snaps onto it (326 g goes to 350 or 325, a third of a cup to a half or a quarter), and a step
down never jumps over the start of its range (75 ml goes to 60). The yield stepper on the
recipe page uses the yield's unit (servings by one and never below one, a yield in millilitres
by its own steps); the amount sheet has the same buttons either side of the amount, following
the unit chosen in the sheet.

**Requests.** "Ask Kitchen…" is in the overflow menu (the three dots) of the
recipe page, of cook mode and of the library, next to "Requests"
(`ui/requests.rs`). It opens a sheet with one text field and Submit: no
photos, no voice, no thread. The request goes into the outbox as a
`ClientOpKind::Request` with a `req_` id chosen on the phone, so it is written
offline too and sent once the server can be reached. What the app attaches by
itself: the recipe, the revision on screen and the scale (recipe page and cook
mode) and the open step (cook mode); a library request has no recipe. The
Requests page (`/requests`) lists every request with its text, status (Queued,
Working, Done, Declined; "Waiting to send" while it is still in the outbox),
date, the agent's note, a link to the recipe, and for a done request a link to
the recipe under "See revision N". It is read-only apart from its own "Ask
Kitchen…" button: replies never appear in Fond. The list is kept in `kv`
(`requests`) for offline, fetched with every sync, and fetched again when
`/api/events` sends `requests`.

**Changes made elsewhere.** A sync runs at launch, on `online`, when the app
returns to the front (`visibilitychange`) or its window regains the focus, and
on every `library` frame, so an agent's edit or another device's change
reaches the library, an open recipe page and the Requests page within a
second. The screens draw from a copy that follows the store only while nothing
is open over them (`ui::settled`):

- With a sheet open (any menu, the amount sheet, the step sheet, Ask Kitchen)
  or the notes field focused, a recipe page keeps the revision it shows and
  the notice "Recipe updated" with Reload appears (the library says "Recipes
  updated", the Requests page "Requests updated"). It is the app-update
  notice's markup and stack, so it sits above the screen, and at the top while
  a sheet is open. Reload shows the new content at once; closing the sheet or
  leaving the field does the same without a tap.
- The notes field is never overwritten while it has the keyboard; it catches
  up when the keyboard goes.
- Cook mode never follows by itself: a session shows the revision it pinned,
  and "Recipe updated" with Reload moves it to the newest one (a `rebase`
  event). The app's own amount change still moves its session at once.
- A redraw of the recipe page keeps the scroll position.

**Chart columns.** Every chart label is horizontal. `logic::chart_widths`
sizes the columns of each block for the width the block really has (measured,
and again on resize), with label widths measured on a canvas in the chart's
font: a step column is as wide as its label up to 120px, where the label
wraps, and never narrower than 64px or its longest word; the ingredient
column takes what is left, at least 130px, and when there is still room the
steps share it, so a small chart fills the width. Only when even the
narrowest columns do not fit does the block get wider than the screen and
scroll sideways under the sticky ingredient column. Columns are rounded to
whole pixels in `ui/chart.rs`. On a short landscape screen Cook moves into
the top bar so it never covers the chart.

**Chart lines.** Which lines the chart draws, which it leaves out, what is
pinned while it scrolls and the WebKit behaviour the CSS works around are in
`docs/fond/chart-borders.md`. In short: strong lines frame a block and every
step, light lines separate the inputs of one step, an input that waits for a
later step has no line inside it, and the pinned ingredient column gets an
edge and a shadow of its own only while the block is scrolled sideways.
Change that note with the chart's CSS.

**View.** The recipe page reads as Steps or as Chart. The one chosen last is
kept on the device (`platform/prefs.rs`, localStorage key `fond.view`) and
every recipe opens in it; with nothing stored a recipe opens as Steps. Cook
mode shares the choice: it opens on Chart when that was chosen last and on
Steps otherwise, and its Steps and Chart tabs store the choice too. Gather is
never stored. Storage that is blocked or throws reads as nothing stored and
drops the write, so the toggle still works for that page.

**Images.** `/img/*` and `/src/*` are immutable and cached by the service
worker, cache-first, in `fond-img-v1`. After each sync the page asks the
worker to fetch every cover thumbnail it does not have; full-size images are
cached as they are viewed. After each sync the worker also deletes cached
`/img/` files whose digest no recipe in the library refers to any more
(`/src/` files stay). `/api/*` is never cached.

`navigator.storage.persist()` is requested at launch. If the phone's copy is
ever evicted, the next launch on the LAN rebuilds it; only an unsent outbox
exists solely on the phone.

## The shell: what scrolls

The document never scrolls. `html` and `body` are locked (`overflow: hidden`,
`overscroll-behavior: none`, `body` fixed to the window), so on an iPhone the
header, cook mode's tabs and the Cook button cannot be pulled with a rubber
band. A screen is a column as tall as the window: its `.bar` header, then one
`.scroller` (`data-testid="scroller"`) that holds everything else, with
`overscroll-behavior: contain`. The scroller's inner block is one pixel taller
than the scroller, so it always scrolls; iOS then bounces that area and never
looks for something behind it. Sideways scrollers inside it (the chart's
`.chart-scroll`, the photo strip) are untouched and keep their own bounce;
the chart's pinned column and lines are as `docs/fond/chart-borders.md` says.
Sheets, notices and the Cook button are fixed to the window as before; a
sheet scrolls by itself (`overscroll-behavior: contain`) and a pull on it or
on the scrim reaches nothing.

What a scrolling document gave for free is done by `platform/shell.rs`:

- **Tap the header to go to the top.** The status-bar tap needs a scrolling
  document. A tap on a bare part of a `.bar` (not on a button, link or field)
  scrolls the screen's scroller to its top.
- **Scroll position.** `navigate` stores the library's scroller position and
  the library restores it on the way back; a new screen starts at its top
  because its scroller is new.
- **Keyboard.** `visualViewport` resize and scroll events set `--kb` on the
  root element to the height the keyboard covers, and the class `kb`. The
  screen ends above the keyboard (`.page` height), sheets sit on it
  (`.sheet` bottom and max height), notices move up, the Cook button is
  hidden, and the focused field is scrolled into view inside its scroller or
  sheet. iOS pans a locked document to reveal a field and can leave it
  panned; the handler puts the window back at 0.

Safe areas: the header pads the notch, the scroller's inner block pads the
home indicator, and the fixed pieces keep their own insets.

## Service worker and updates

`build/precache.sh` runs as a trunk post-build hook. It lists every file of
the build and prepends two constants to `js/sw.js`: `SHELL` (the URLs, with
`index.html` as `/`) and `BUILD` (a checksum over those files and the worker
source). The worker precaches `SHELL` into `fond-shell-<BUILD>` and serves
the shell from it: navigations to `/`, `/r/*`, `/cook/*`, `/inbox` and
`/requests` get the cached `index.html`, so those addresses load offline.

A deploy changes `BUILD`, so the browser installs the new worker beside the
running one:

1. The new worker precaches into its own cache and waits.
2. If the app is open, it shows "A new version of Fond is ready." with an
   Update button; nothing reloads under a cook.
3. At the next launch (or on that tap) the app tells the waiting worker to
   take over and reloads once into the new shell.
4. On activation the new worker deletes every other `fond-shell-*` cache.

The app asks the browser to check for a new worker at launch, each time it
returns to the front, and when the server's `build` (in `hello` and sync
answers) changes.

The server must serve `/sw.js` and `/` with `Cache-Control: no-cache`,
`/sw.js` as JavaScript and `/manifest.webmanifest` as
`application/manifest+json`.

Images go out a few at a time. A long library asks for every cover at once,
and the server refuses requests over its limit of 32 in flight with a 503.
The service worker sends at most six image requests at a time and asks again
for a refused or failed one (four tries); the page asks again for a picture
that fails to load (three tries, `platform/shell.rs`), which covers a first
visit the service worker does not control yet.

## Build

```bash
cd crates/omni-recipes-web
trunk build --release            # writes dist/, including dist/sw.js
```

Tool versions are pinned in `Trunk.toml` and `deploy/web-tools/install.sh`
(the same as `omni-web`). The Docker web stage builds both bundles and ships
this one, with Brotli and gzip siblings, at `/app/recipes-web`
(`OMNI_RECIPES_WEB_DIST`). Icons: edit `brand/icons.py`, bump its `VERSION`
when the artwork changes (iOS caches Home Screen icons by URL), update the
file names in `index.html` and `manifest.webmanifest`, and run it.

## Test

```bash
cargo test -p omni-recipes-web        # the pure logic, natively
cargo xtask gate                      # includes wasm32 clippy for the crate

# In a browser, against the mock server:
python3 crates/omni-recipes-web/dev/mock-server.py --port 8787   # serves ../dist
cd crates/omni-recipes-web/e2e
npm ci && npx playwright install webkit                           # once
FOND_DIST=../dist npx playwright test
```

The mock server (Python standard library only) implements the contract in
memory, seeded with the four golden recipes of `omni-recipe-format` and the
preview seed's small three-step recipe, and has
`/__mock/*` helpers to play an agent (`note`, `revise`, `import`, `reset`,
and `requests` and `request` for `recipes_requests_list` and
`recipes_request_update`).

The browser tests run in WebKit at iPhone size and cover the library, search,
the tag filter, both recipe views (asserting `rowspan`/`colspan` and that
every chart table is tiled), the chart of every recipe in the library in the
recipe view and in cook mode (no vertical or rotated text, no label that does
not fit or breaks inside a word, a table that fills its container unless it
scrolls), the chart's lines and pinned column at several sideways scroll
positions (`chart-borders.spec.js`), the remembered view
(`view-preference.spec.js`), the shell (`shell.spec.js`: the document cannot
scroll, headers and the Cook button stay put when content is pulled past
either end, the header tap, sheets, and the keyboard played by shrinking the
visual viewport; the bounce itself is only on a real iPhone), scaling, notes, archive and delete with undo, cook mode in all three
tabs with recipe notes, timer, reload and finish, leaving and discarding a cook,
changing an amount (recipe view, scaled page, cook mode, offline), the inbox
upload, the manifest and icons, and the app offline with writes sent on
reconnect. `mock-only.spec.js` adds what needs the mock (it runs when
`FOND_DIST` names the served dist directory): the update flow, a recipe revised
during a cook, an agent's note, the retired adjustment events of an app not
yet updated, the absence of any cook-only wording in the built app, the
"While … runs" offers, the
server-pinned session document, and an imported inbox item.
`library.spec.js` covers the masonry at phone width and wider (dealt in reading order, cards
at their own height, 22px apart, lazy covers, scroll restore), pinning from both menus,
reordering by a held drag and by the card menu, a list set elsewhere, and the steppers of the
amount sheet and the yield in every unit family the library has. It pins the library's first
two recipes and unpins them, and saves no amount, so it also runs against a real Omni.
`requests.spec.js` covers "Ask Kitchen" from the three menus with the context
each attaches, the Requests page, a request written offline, an agent working
a request through to a done revision while the app follows, and the "Recipe
updated" notice under a sheet, with the notes focused and in cook mode. The
agent is played by `agent.js`: through the mock's helpers, or with
`FOND_AGENT=claude` through the real MCP tools, each call made by a fresh
`claude -p` client (slow: about twenty seconds a call). Against a real Omni it
needs a throwaway recipe named by `FOND_RECIPE_REQUEST`; it writes revisions
to that recipe and leaves its requests closed, marked as test requests.
The rest take the server from `FOND_BASE_URL`, so the same suite runs against
a real Omni:

```bash
FOND_BASE_URL=https://recipes.syas.ca FOND_E2E_SKIP_FINISH=1 FOND_E2E_SKIP_INBOX=1 \
  FOND_E2E_SKIP_AMOUNT=1 FOND_RECIPE_CHART="…" FOND_RECIPE_COOK="…" npx playwright test
```

Against the real server locally, use its preview (`docs/recipes.md`, "Running
it locally") with `FOND_BASE_URL=http://fond.localhost:8099`; nothing needs
skipping there. `FOND_CHROMIUM=1` adds a Chromium project at phone size
(`--project chromium`, after `npx playwright install chromium`), which is how
the content security policy is checked in both engines. Requests the tests
make themselves carry an `Origin` header, because Omni refuses writes from
another origin.

Tests that change data put it back. Two cannot (a finished cook stays in the
cook history; an uploaded photo waits for an agent) and are skipped with the
two switches above. Every session a test starts and does not finish is
discarded (`abandon`), so no run leaves a cook open; the chart test skips cook
mode for a recipe that already has an open session, which is not its to
discard. The amount tests put the amount back, but each change and each undo
is a revision in the recipe's history: `FOND_E2E_SKIP_AMOUNT=1` skips them,
and `FOND_RECIPE_AMOUNT` and `FOND_AMOUNT_INGREDIENT` name the recipe and the
ingredient id they edit (an ingredient whose amount the step text quotes). `FOND_SHOTS=<dir>` writes light
and dark screenshots of each screen. `FOND_CHART_SHOTS=<dir>` writes every
chart block of every recipe at each sideways scroll position, in the recipe
view and in cook mode.
